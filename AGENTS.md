16. Public/private/no-ticker company research must be useful without fabricating identifiers or private financial facts.
17. Provenance, assumptions, as-of/freshness and evidence are product behavior, not optional debug metadata.
18. Preserve working functionality unless a reproduced defect or canonical migration requires change.

**Market Data; Company Fundamentals; Valuation; Portfolio & Risk; Fixed Income; Derivatives; Macro & FX; Alternative Assets; Corporate Actions & Events; Research & Reporting; Personal Finance & Wealth.**

## 12. Verification / CI / merge discipline

Canonical validation policy: `docs/technical/LIOS_PROGRESSIVE_VALIDATION_CI_STRATEGY.md`.

Before merge, fetch current `main` and reconcile divergence.

**Local/targeted validation is the implementation loop. GitHub Actions are not.**

Use:

> **V0 FAST LOCAL → V1 FOCUSED TASK → V2 INTEGRATION WHEN REQUIRED → V3 SHIPPING GATE → V4 RELEASE GATE**

### Risk classes

- `R0` — docs/comments/metadata: V0/structural validation;
- `R1` — isolated low-risk implementation: V0 + V1;
- `R2` — normal capability work: V0 + V1, selected V2 when interfaces cross systems;
- `R3` — shared-core/security/schema/runtime/identity/authority: V0 + V1 + mandatory relevant V2;
- `R4` — Shipping Point/release candidate: V0 + V1 + V2 + V3, then V4 where release evidence applies.

Risk is based on blast radius, not line count.

### Full Quality Gate policy

The complete `LIOS Quality Gate` is **not** the default PR/push gate.

Run it deliberately for:

1. `SP-01`…`SP-07` candidates;
2. P14/release candidates;
3. explicitly justified exceptional R3 checkpoints where whole-repository regression confidence materially matters.

Do not trigger the full gate for ordinary PR creation, every small push, documentation-only work or as a substitute for diagnosing a focused failure.

No agent may skip V0/V1 focused testing merely because V3 will occur later at a Shipping Point.

### V0 / V1

Run the smallest safe test set proving the changed behavior. Include known-answer/reconciliation tests for changed numerical logic, and affected browser/client smoke when the user flow changed. Record exact commands/outcomes.

### V2

Required for material shared-core changes and meaningful cross-system integration milestones. Test the relevant integrated journey, not automatically the whole repository.

### V3

The normal complete-gate boundary for `SP-01` through `SP-07`. Execute the full Quality Gate plus the Shipping Point's real MSJ, applicable package/target proof and protected prior-SP regression journeys.

### V4

Final release qualification: cross-platform, signing/notarization, clean-target, upgrade/rollback and P14 evidence as applicable.

### Failure discipline

A full gate is confirmation, not a debugging loop. If V3 fails:

> **identify failing subsystem → reproduce V0/V1 → fix → relevant V2 → one final V3 confirmation**

Do not repeatedly rerun all gate steps without a diagnosed change.

### GitHub Actions / runner budget discipline

- Local focused testing is the default.
- The owner's self-hosted Mac is the primary V2/V3 desktop/integration runner where it can faithfully prove the target.
- Avoid concurrent heavy packaging, Docker/PostgreSQL, browser/Electron, Python-full-suite and full-gate jobs on the same owner Mac.
- Preserve stale-run cancellation where the result no longer matters.
- Hosted runners are reserved for target evidence the self-hosted environment cannot faithfully supply, especially Windows/cross-platform/final release qualification.
- Specialist visual, RLS, cross-platform and release workflows are deliberate/manual unless a later owner decision changes them.
- A billing/runner failure that prevents code execution is not a code pass or code failure; record it honestly.
