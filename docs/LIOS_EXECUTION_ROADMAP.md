1. The goal is concurrent progress **without** multiplying authorities, branch drift or false completion.

### 0.0.1 Why this program exists

LiOS must not become either a conventional module dashboard or a generic chatbot with a finance skin.

The target operating model is:

> **The user operates LiOS through intent. LiOS operates the terminal for the user.**

The primary interaction loop is:

> **PROJECT → CHAT → INTENT → ROUTE → COMPUTE → EXPLAIN → ARTIFACT → NEXT ACTION**

Equivalent execution shorthand:

> **ASK → ROUTE → COMPUTE → EXPLAIN → MATERIALIZE → ACT**

The user should be able to say:

> “Analyse MSFT Q3 earnings versus consensus and build a DCF with WACC sensitivity.”

without first navigating Market Data → Fundamentals → Filings → Consensus → Valuation → DCF → Sensitivity.

LiOS resolves the required entity/entities, data, deterministic engines, connected sources and permitted BYOAI automatically; exposes the selected capabilities compactly; executes governed work; returns finance-native structured results; materializes durable professional Artifacts; keeps those Artifacts active as conversational context; and presents the next useful actions.

The product moat is therefore not the appearance of a chat UI. It is the combination of:

- durable Projects and task-oriented Chats;
- hidden but governed Working Context;
- provider-neutral BYOD and BYOAI;
- authoritative deterministic finance engines;
- source/evidence/trust lineage;
- typed living Artifacts;
- conversational control plus direct manipulation;
- automatic contextual Next Actions;
- proactive continuous intelligence;
- exact continuity into expanded Workbench;
- immutable revisions, evidence and history.

### 0.0.2 Locked product behavior

These decisions are settled unless the user explicitly reopens them.

#### Entry and restoration

1. A returning authenticated user restores the exact last valid Project / Chat / active Artifact state where possible.
2. New Chat always gives a clean, simple Ask LiOS surface.
3. A brand-new authenticated user does **not** need to create a Project before asking a question. The first useful surface is a clean conversational workspace; Project creation is optional.
4. Signed-out/public preview remains non-executable. No anonymous AI, research, connector, Project, Chat, Artifact or deterministic-engine execution.

#### Project, Chat and Artifact mental model

1. **Project = durable intelligence environment / case / subject.**
2. **Chat = one task, investigation or analytical thread inside or outside a Project.**
3. **Artifact = durable professional work product.**
4. **Workbench = expanded analytical canvas for the same work, not a second application.**
5. Project examples may include a single company, a portfolio, an M&A case, a macro theme, a consulting engagement or a personal-finance case.
6. Chats under one Project may include “Earnings analysis + DCF”, “Peer comp table”, “Risk factor breakdown”, etc.
7. Important work inside a Project must auto-persist as an Artifact (required target; current source requires explicit Keep, pending TC-13/P4 integration); Quick/Temporary work still requires an explicit Project destination before becoming durable.

#### Automatic routing

1. Fully automatic routing is the default. LiOS chooses compatible connected sources, deterministic engines and permitted BYOAI.
2. The user does not have to choose a module before asking.
3. Engine/capability/provider names appear compactly, e.g. \`FUNDAMENTALS · DCF · BYOAI\`.
4. Capability tags are informational by default. Clicking them may explain what LiOS selected and expose advanced overrides.
5. Source scope, deterministic-only mode, AI-direct mode, provider selection and other advanced controls remain available but are progressively disclosed rather than permanently visible.
6. If a material ambiguity changes the computation or meaning, LiOS asks rather than guessing.

#### Working Context

LiOS maintains a **hidden Working Context** for every conversation. It is an internal orchestration object, not a user-facing inspector.

The Working Context must be capable of carrying, as applicable:

- Project id and name;
- Chat id/scope/branch;
- inferred entity/security/entity-set;
- active Artifact and version;
- selected Artifact/dashboard element;
- current task/objective;
- source posture and relevant source policy;
- current assumptions and assumption references;
- as-of date / latest-vs-as-known-on posture;
- resolved capabilities;
- permitted AI posture/provider preference;
- relevant recent execution/request/receipt references;
- inferred contextual confidence;
- current workspace/session reference when expanded.

Rules:
- Quick Chat may retrieve relevant private sources under the approved scope in §0.0.12; Temporary Chat has no implicit private-context inheritance. Tenant/client restrictions and exclusions remain authoritative.
- Temporary Chat Working Context remains ephemeral.
- The normal user never has to open, edit or understand this object.
- Selection of a dashboard metric, chart point, model assumption, table cell or document fragment may temporarily enrich the hidden context.
- If inferred context becomes materially ambiguous, ask.
- The hidden context may internally retain an inferred entity for continuity, but there is **no formal user-facing active-entity selector**.

#### One LiOS identity

Users interact with **one LiOS**. Specialist valuation/research/portfolio/risk/data/AI agents may exist internally, but they are not separate visible personalities the user must summon or manage.

#### Composer

Default composer is intentionally minimal:

- \`+ / Tools\`;
- Ask LiOS input;
- optional voice affordance when actually available;
- Send.

Attachments, source controls, resources, session controls, provider controls, deterministic-only/AI-direct posture, Workbench expansion and secondary operations are available contextually or through \`⌘/Ctrl+K\`; they do not permanently occupy the composer.

#### Execution visibility

The runtime remains fully governed, but the default user-facing execution presentation is compact and understandable:

- \`Routing → Fundamentals + Valuation + BYOAI\`
- \`Fetching → SEC EDGAR + connected consensus source\`
- \`Calculating → FCFF DCF\`
- \`Building → Valuation Artifact\`

After completion, collapse to a compact receipt such as:

- \`4 steps · 3 sources · 3.8s · Show work\`

Detailed steps, permissions, receipts, methodology, gaps, conflicts and source evidence remain available through Show Work / Evidence.

#### Answer rendering

1. User prompts may appear as compact right-aligned/tinted request cards.
2. LiOS responses should mostly live directly on the workspace instead of inside large assistant chat bubbles.
3. Finance output follows **structured evidence/numbers first, concise interpretation second**.
4. Typed tables/charts/metrics are preferred over markdown pretending to be a professional analytical object.
5. Markdown remains a fallback.

#### Artifact sidecar and active Artifact behavior

1. Substantial Artifacts auto-open in the right pane; lightweight inline results may remain inline until opened.
2. Default sidecar width is approximately **348px**, but it is resizable and supports Artifact Focus/expanded mode.
3. One Artifact is active at a time; a compact switcher may move among multiple Artifacts.
4. Opening/selecting an Artifact updates hidden Working Context.
5. \`ARTIFACT / EVIDENCE / HISTORY\` is the canonical trust triad:
   - **Artifact:** professional work product;
   - **Evidence:** sources, calculations, assumptions, methodology, receipts, conflicts/gaps;
   - **History:** revisions, comparisons and changes.
6. Asking “change WACC to 9%” while the DCF is active operates on that Artifact.
7. Durable changes create a new immutable revision; history is not overwritten.
8. AI-proposed material mutations retain review/approval semantics.
9. Explicit direct user manipulation of deterministic model controls is user intent and may recompute immediately while recording a new revision.
10. Conversation and Artifact are two views of the same work: selection in either may become context for the other.

- Build peer comps;
- Show risk factors;
- Compare prior quarter;

- Create memo;

- Open Evidence;

#### Project Home

Project Home is deliberately **richer** than the global/new-chat surface.

It is an adaptive intelligence dashboard, not a mandatory dashboard builder and not a static template. Depending on the Project, it may contain:

- Project summary;
- What Changed;
- important Signals / attention items;
- key verified metrics;
- live / recently updated Artifacts;
- recent Chats;
- catalysts / events / calendar;
- active Automations / alerts;
- relevant entities and relationships;
- source/data/AI health when useful;
- compact activity/intelligence timeline;
- pinned user priorities/goals.

There is **no permanent dedicated Decision area**.

Behavior:
- LiOS may reorder unpinned modules based on materiality/relevance.
- User-pinned modules remain fixed.
- Different Project contexts naturally produce different useful modules without requiring a Project-template gate.
- Project Home quietly refreshes whenever permitted.
- Quantitative cards retain source/as-of truth internally.
- If refresh is unavailable, show the last verified state/as-of or an explicit unavailable/data-gap state; never imply freshness.
- Any relevant dashboard number/chart/item may become conversational selection context (“Why?”, “Stress this”, “Compare this”).
- Project goals/thesis/instructions may guide proactive intelligence.
- What Changed uses a meaningful baseline: previous filing, consensus, previous Artifact revision, Project thesis or other contextually correct baseline—not blindly the previous scalar observation.

#### Proactive intelligence — high autonomy

LiOS is intentionally **highly proactive**.

Permitted autonomous behavior may include:
- detect meaningful source/data changes;
- run read-only deterministic analysis;
- run permitted BYOAI synthesis within Project/user cost policy;
- refresh Project Home;
- surface material risks, contradictions and missing evidence;
- challenge an existing thesis with counter-evidence;
- prepare living Artifact revisions;
- create a substantial sibling Chat when a durable new analytical thread is justified;
- rank overnight/multi-event changes by materiality, relevance, Project goals, recency and evidence quality;
- group low-priority changes instead of flooding the interface.

Rules:
- Prefer event-driven updates when supported; otherwise use intelligent scheduled checks.
- Deduplicate repeated observations/work.
- Apply relevance thresholds and cooldowns.
- Routine proactive intelligence stays inside LiOS.
- OS notifications are reserved for explicit alerts, important automations, long-job completion or genuinely time-sensitive events.
- Background BYOAI has user-configurable Project permission and cost/budget limits.
- Deterministic/local read-only work may run within sensible resource limits.
- Consequential external actions—sharing/sending, external mutations, purchases, trading or equivalent—remain governed and must never occur silently.
- No brokerage execution/copy trading enters current scope.

#### Living Artifacts

Artifacts are not static saved files.

When upstream evidence materially changes:
1. detect dependency impact;
2. refresh deterministically where permitted;
3. create a new revision rather than overwrite the old one;
4. compare old vs new;
5. surface the material delta;
6. retain evidence/provenance for both versions.

Example:
\`DCF updated · base value -4.8%\`

A Project dashboard may quietly refresh current state; a durable model/report still maintains versioned intellectual history.

#### Source conflict behavior

If two material sources disagree:
- preserve both observations and their source/as-of state;
- reconcile only when deterministic rules/semantics make reconciliation valid;
- otherwise show the conflict;
- do not silently choose the “best” value merely to keep the flow moving.

#### BYOAI routing

1. Users/Projects may define preferred model/provider posture.
2. LiOS may automatically route among allowed connected models when useful.
3. Provider allow/deny, transmission policy and Project policy remain authoritative.
4. AI does not replace deterministic calculator-of-record behavior.
5. Background AI work obeys budget/permission controls.
6. BYOAI inference is not silently converted into LiOS credit consumption.

- Project;
- Chat;
- current Artifact;
- dashboard/Artifact selection;
- latest request;
- current task.

Multi-entity work is natural. An internal Project entity graph may improve routing and proactive intelligence, but the graph is not a mandatory prominent UI surface. Expose relationships visually only when useful.

Entering expanded workspace preserves:
- Project;
- Chat;
- hidden Working Context;
- active Artifact/version;
- relevant entity/entity-set;
- assumptions;
- source posture;
- analytical/session state.

Expanded Workspace adds professional depth such as:
- multiple charts/panes;
- docking;
- spreadsheet/model editing;
- large data exploration;

Returning exits back to the same conversation and active work object. Workbench must never become a parallel primary application.

- actually connected providers/sources;
- active BYOAI provider;

### 0.0.3 Research-informed design principles

Terminal Convergence adopts the following patterns because they fit LiOS's product contract:

- **Project-based persistent context:** durable work should outlive a single chat and remain scoped.
- **Conversation + side-by-side professional object:** users should be able to talk to a model/report/chart while directly manipulating it.
- **Evidence on demand:** provenance must be available without flooding the primary answer surface.
- **Progressive disclosure:** advanced controls remain accessible without permanently occupying the primary layer.
- **Direct manipulation:** deterministic model controls should give immediate, reversible, versioned feedback.
- **Ambient/proactive intelligence with permission boundaries:** useful background work should happen automatically, while external side effects remain governed.
- **One assistant identity:** internal orchestration complexity must not become a swarm of visible agent personas.
- **Provider/data truth:** capability/connection/status UI must represent actual entitlement and source state, not aspirational availability.

These are interaction patterns, not instructions to copy another product's branding or trade dress. LiOS retains its own graphite/gold visual system and professional terminal identity.

#### B. Research experience and architecture requirements

1. **One conversation surface.** General questions, web research, private-data questions and financial workflows use the same composer and runtime. Follow-ups retain task, source, time and active-Artifact context. Users do not select modules or agent personalities.
2. **Separate capabilities.** Model completion, tool calling, structured output, image input, embeddings, web retrieval and native provider grounding are distinct capabilities. A valid AI key does not imply web access. Extend the existing registry/router with tested capability information; do not create another router.
3. **Provider-neutral research.** Support external search adapters and native grounded provider paths where verified. Normalize their citations, usage, errors and source metadata into LiOS contracts. Initial implementation proves one search provider plus the existing BYOAI path; expand only after acceptance.
4. **Evidence before synthesis.** Retrieve actual permitted passages/results, not merely result titles or dataset profiles. Preserve source identity, content version/hash, location, source class, publication/effective/retrieval timestamps, entity/period, access policy and extraction state. Differentiate fact, user assertion, calculation and AI interpretation.
5. **Grounded answers.** Associate factual assertions and comparison cells with evidence references; show conflicting sources and missing coverage. URL presence or matching a number is not claim verification. Record searches, source failures, coverage limits, fallback and cost in Show Work without exposing hidden reasoning.
6. **Private documents.** Use the existing ingestion/Docling path; preserve structured page/table/location anchors, revision and deletion propagation. Evaluate lexical plus semantic retrieval only against a measured corpus. Optional vector acceleration is not a shipped hybrid-search claim.
7. **Firm databases.** Discover allowed schemas/tables; propose entity, column, unit/currency, fiscal-period and relationship mappings; confirm material ambiguity before computation. Use live bounded queries for structured data, with reviewed query plans and lineage. Do not embed all rows into document chunks or claim any database automatically has valid financial semantics.
8. **Database boundaries.** Read-only credentials/transactions, table/function allowlists as appropriate, execution timeout, memory/row caps before full buffering, cancellation and restricted filesystem/network access are required. A SELECT/WITH/EXPLAIN/PRAGMA prefix alone is insufficient. Enforce engine-specific behavior.
9. **Finance authority.** Deterministic engines own calculations. Validate entity + metric + sign + unit + currency + period + value + evidence, not numeric occurrence. User prompts are assertions/inputs, not automatically authoritative evidence. Explicitly approved AI estimates remain labelled AI-derived.
10. **Memory.** GM-19 owns durable memory; TC/P2 Working Context remains bounded live state, with P7 indexing/snapshots and P3 history preserved. Retain origin, scope, inference status, revisions and inspect/correct/delete controls. Revocation/deletion propagates to retrieval caches and derived memory; no Temporary contribution, secrets or financial-evidence substitution.
11. **Reusable tasks.** Reuse existing WorkflowPlan/action/automation infrastructure. A saved task is a versioned reusable recipe, not a scheduled job or credential snapshot. Store parameter schema, source requirements, output type, policy references and recipe version. Reruns recheck permission, freshness and required inputs. Scheduling requires a separate explicit choice.
12. **Comparison Artifacts.** Produce company/document/topic comparison tables automatically when appropriate; each supported cell opens evidence. Distinguish zero, missing, unavailable and not applicable. Preserve source revisions and export provenance.
13. **Fallback.** Apply entitlement, source suitability, temporal meaning, user exclusions and provider policy before choosing alternatives. Never silently send private data to a disallowed model or change valuation semantics to complete a request.
14. **Budgets.** BYOAI means provider inference is not silently billed as LiOS tokens. Search/extraction/embeddings/local compute/storage/background research still have costs. Track usage where available, label estimates, enforce bounded runs and cancellation, and disclose provider costs rather than promise zero cost.
15. **Research trust.** Treat retrieved content as data rather than tool instructions. Enforce permissions outside the model, filter access before retrieval, prevent secrets appearing in prompts/logs/Artifacts, and test hostile documents and source revocation.
16. **Availability.** Generative synthesis requires a working permitted AI connection; deterministic analytics and ordinary retrieval do not. Web answers also require a usable retrieval capability. Unsupported capability, missing credentials, quota exhaustion and offline status must produce truthful, recoverable states.

Example acceptance request: “Compare our investment memo with the latest company disclosures and web coverage. Check the assumptions against our database and update the valuation.” Required path: resolve scope/entity/time → permitted passages and bounded queries → evidence normalization → deterministic analysis → grounded synthesis → inspectable citations → versioned Research/Valuation Artifact → follow-up/refine/save task. Missing market quotes must not block independent qualitative research.

7. classify the imported subsystem as Production / Adapt / Stub / Reject;

## P3 implementation lock — Ledger, reproducibility and change intelligence (2026-09-22)

P3 is implemented as one LiOS-owned, append-only evidence layer across P1 Projects/Sessions and the P2 governed Conversation Runtime.

- **LIOS-P3-01:** persistent Project/Quick-Chat Ledger streams use ordered sequence numbers plus SHA-256 previous-hash/event-hash chaining. Temporary Chat remains intentionally non-persistent.
- **LIOS-P3-02:** conversation requests, workflow plans, approvals, execution receipts, user decisions and Session mutations become typed Ledger events rather than transcript-only history.
- **LIOS-P3-03:** Session ancestry, common-ancestor discovery and structured branch comparison are first-class server contracts.
- **LIOS-P3-04:** Show Work resolves a persisted reproducibility receipt containing source references, input/output hashes and snapshots, formulas/method, engine/version, as-of metadata, warnings and explicit AI involvement.
- **LIOS-P3-05:** Ledger events are append-only. Reversible Session mutations carry an inverse payload; Undo applies the inverse in a transaction and appends `state.reverted` instead of deleting or rewriting history. A database uniqueness guard prevents concurrent duplicate reverts.
- **LIOS-P3-06:** the LiOS lineage graph standardizes source/input/formula/engine/model/assumption/provider/decision/conversation/execution/session/artifact/policy/workspace nodes and normalized relations without making an external lineage framework authoritative.
- **LIOS-P3-07:** Session provenance records layout-state, source-policy, strategy, backtest, assumption and artifact-version references; create/fork/update/archive/restore operations enter the same change graph.
- **LIOS-P3-08:** deterministic change intelligence explains material Session/branch differences using stored ancestry, analytical state, context, source-policy, strategy, backtest, assumption and artifact-version references. Persistent P4 artifact internals are not invented early.
- **LIOS-P3-09:** P2 execution receipts are promoted into P3 reproducibility evidence with provider observations, point-in-time/as-of metadata where available, engine/formula attribution and artifact-draft lineage. Later P4/P5 versions enrich the same contract rather than replacing it.
- **LIOS-P3-10:** Project/Session portability uses an explicitly versioned, credential-free manifest with Session state hashes and Ledger stream heads. Full package export/import remains P4.

**P3 security/privacy lock:** Ledger payloads are tenant-scoped and recursively redact credential-shaped fields. API keys, access/refresh tokens, passwords, authorization values, cookies, private keys and OS-vault credentials are never valid portability content.

**P3/P4 boundary:** P3 owns evidence, history, lineage, branch comparison and reproducibility. P4 owns persistent Artifact lifecycle/versioning/rendering. P3 may reference P2 work-product drafts and future artifact-version refs but does not create a competing artifact store.

**P3 gate:** a persistent LiOS workflow can be traced from conversation/request through governed execution to reproducibility evidence; a Session can be forked and deterministically compared to its ancestry; reversible Session changes can be undone without rewriting history; the Project Ledger can verify its hash chain and produce a credential-free portability manifest.
