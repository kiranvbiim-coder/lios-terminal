# LiOS V4 — P3 Production Services & Control Plane

> **Superseded in part (2026-10-02).** This document was written for the earlier LiOS-hosted model. Since GM-07 a customer install contacts no LiOS service: identity is local, entitlement is a vendor-signed licence file, billing/credits/webhooks are gone from the product, and there is one auth stack and one web bundle. Where this text describes a hosted control plane, Paddle billing, a credit wallet, `LIOS_CONTROL_PLANE_URL`, `/api/client/auth/{login,logout,me,register}` or `/client-terminal/`, read `docs/technical/OPENCLAW_ASSIMILATION_BLUEPRINT.md` §40–§45 instead.

> **Authority:** `AGENTS.md`, `docs/LIOS_SUPER_INTELLIGENCE_EXECUTION_PLAN.md` and `SUPER_INTELLIGENCE_SHIPPING_POINT_CONTRACT.md` govern SI-01–SI-07/SP-01–SP-07. S0–S10 validate; CP phases and V4/LV4 ledger IDs are historical. GM/TC/CA/P owners stay singular, P14 remains final release authority, and privileged `exec.*` requires GM-11.

> Objective: qualify distribution and applicable local/user-operated operational controls without a vendor customer runtime. Home owns `/api/auth/*`, local identity/trial and imported vendor-signed licences; one auth stack and one build serve supported user-owned infrastructure.
> Machine-readable status: `GET /api/operations/production-acceptance`  
> CI accounting contract: `npm run acceptance:production`

## Status semantics

- **[x] Recorded code contract** — the initial P3 ledger recorded implementation/accounting, not fresh execution.
- **[~] Target evidence pending** — an applicable real target/customer action needs dated evidence.
- **[!] External blocker** — required signed distribution, selected user-provider or target evidence cannot be fabricated. Paddle is not a current prerequisite.
- “Configured” never means “exercised.” Legacy ledger endpoints below do not establish current exposure or qualification.

## Retention, purge and deletion receipts

- [x] Durable platform retention policy table with bounded telemetry/legacy-relay-metadata/deletion/export retention windows.
- The initial hosted deployment recorded startup/24-hour purge and confirmation-gated organization/manual purge. These are historical scheduling/configuration claims, not a requirement to run vendor services.
- For supported user-operated metadata stores, verify the actual retention worker and deletion scope on that target; Desktop Local does not inherit a hosted purge worker or require `DATABASE_URL`.
- Expired applicable diagnostic/receipt metadata must be purged subject to legal hold.
- Automatic/manual deletion must retain counts-only auditable receipts and explicit confirmation where required.
- [x] Organization purge generates an auditable deletion receipt.
- [x] Receipt storage contains counts/status/reason, not deleted payload contents.
- [~] Where retention/deletion is applicable, retain a dated target purge receipt and approved organization deletion exercise. Do not infer target support from the old hosted ledger.

## Local-only export custody

- [x] Shared XLSX/PDF exporters hash generated bytes locally.
- Export bytes and readable filenames remain local/user-owned. The historical hosted flow sent only content/filename hashes, format, byte size and time; no vendor transmission or central receipt is a current prerequisite.
- [x] Export file/report bytes are never uploaded through the custody flow.
- Any supported user-operated receipt store must retain `artifactNameHash`, not the readable artifact name.
- [x] Custody is hard-coded/database-constrained to `local_only`.
- [x] Users can tombstone their own active custody receipts.
- Authorized organization compliance/admin review applies only to its supported user-operated receipt store.
- [~] Exercise a real local export, inspect its hash/integrity and reopen it; retain user-custodied evidence. Qualify optional user-operated receipts separately.

## Redacted diagnostics and crash telemetry

- [x] Remote diagnostics are disabled by default.
- Historical `/api/client/diagnostics/config` sink enablement does not authorize upload. Current remote support diagnostics require explicit time-bounded user consent and redaction before leaving Home; no vendor sink is required.
- [x] Accepted diagnostic details use a narrow allow-list of counters/codes.
- [x] Detailed local telemetry remains localStorage-only.
- [x] Aggregate upload excludes raw queries, capability names, notes, uploaded data, model inputs, provider credentials and report bytes.
- [x] React root crashes are SHA-256 fingerprinted locally; full stack is not transmitted.
- Server incidents in supported user-operated deployments must retain fingerprint/status/method metadata, never bodies/full stacks.
- Applicable diagnostic retention must honor expiry and enterprise legal hold.
- [~] Privacy/security review and explicit user consent precede any optional remote diagnostics; `LIOS_TELEMETRY_ENABLED` alone is not consent.
- [~] Where diagnostics are offered, retain exact-target aggregate-event/crash-fingerprint evidence, not an assumed vendor production event.

## P3 formal exit

The recorded P3 code exit was an authoritative Quality Gate pass on the exact merged commit; it does not certify the present build.

Current qualification requires dated evidence for signed distribution/update metadata and the applicable local/user-operated retention, legal-hold deletion, export integrity, consented diagnostics/crash fingerprint and selected notification paths. Historical Paddle projection, hosted purge and central export receipts are not active prerequisites.

Every applicable SP-01–SP-07 requires a real MSJ, packaged/target execution, no fake success, protection of accepted behavior and exact commit/build/topology/check/outcome/limitations evidence. P14 retains final release authority. No Shipping Point acceptance or missing deployment evidence is fabricated or inferred from ledger rows/environment names.
