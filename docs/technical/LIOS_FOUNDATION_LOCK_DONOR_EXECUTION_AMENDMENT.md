## 0. Purpose and authority

This document is an amendment to the existing Super Intelligence execution program. It is **not** a competing master plan, architecture, donor policy or subsystem authority.

The canonical program remains:

> **SI-01 → SI-02 → SI-03 → SI-04 → SI-05 → SI-06 → SI-07**

This amendment strengthens how that program is executed by adding:

1. a **Foundation Epoch** covering SI-01 through SI-04;
2. a **Foundation Lock** after SP-01 through SP-04 are accepted;
3. an aggressive donor-use directive covering the full 92-donor baseline;
4. standing authority for agents to discover, inspect, fork and assimilate additional suitable donors without asking the owner for permission each time;
5. mandatory repository recording for all material donor decisions;
6. a clear separation between donor maintenance posture and permission to use the donor.

Where wording in older issue comments or historical plans conflicts with this amendment, the current canonical documents plus this amendment plus the latest owner directive in issue #192 control execution. This amendment does not transfer canonical subsystem ownership.

- avoid donor-by-donor product duplication.

# 4. Donor layers are organizational, not permission boundaries

## 4.1 Layer A — Controlled donor mirrors

Controlled mirrors are donor repositories forked or deliberately maintained under the owner's GitHub account.

Current examples include OpenClaw, browser-use, CUA, GraphRAG, Qlib, FinRobot, TradingAgents, FinGPT, LangAlpha and dexter-js.

Typical reasons to keep a controlled mirror:

- repeated inspection;
- substantial LiOS-specific modification;
- stable exact source reference;
- selective upstream synchronization;
- patch maintenance;
- multi-phase strategic use;
- experimentation or benchmarking.

A fork is only a working copy. It does not change the upstream license and does not create a LiOS authority.

## 4.2 Layer B — Documented/on-demand donor universe

All documented donors outside the current controlled-mirror set remain **fully usable**.

Layer B donors may be:

- inspected;
- cloned;
- forked;
- imported;
- consumed as packages;
- adapted;
- modified;
- repurposed;
- combined with other donors;
- used as runtime components;
- used as reference validators;
- used as challenger implementations;
- promoted to controlled mirrors.

There is **no rule requiring a Layer B donor to remain documentation-only**.

If a documented donor is useful:

> **USE IT.**

If a fork materially improves implementation or maintenance:

> **FORK IT.**

If only one package, algorithm or mechanism is useful:

> **USE ONLY THAT PART.**

If a complete permissively reusable subsystem is stronger than a new implementation:

> **IMPORT OR ADAPT THE SUBSYSTEM BEHIND THE CANONICAL LIOS OWNER.**

There is no arbitrary numerical limit on controlled forks. Avoid unnecessary forks because of maintenance cost, not because of policy restriction.

# 5. Standing authority for new donor discovery

Agents are explicitly authorized to discover new donors during execution.

Prior owner permission is **not required** merely to:

- discover;
- inspect;
- evaluate;
- benchmark;
- clone;
- fork;
- pin;
- adapt;
- combine;
- or integrate a suitable donor into an already authorized LiOS workstream.

This standing authority exists so a stronger implementation can be used immediately instead of waiting for another owner decision.

The permission is conditioned on all mandatory safeguards in this amendment and the canonical donor policy.

Any newly discovered donor used materially must be recorded in the repository.

The record must include, where applicable:

- donor name;
- upstream repository;
- controlled fork/mirror repository if created;
- exact commit/tag/version;
- relevant source paths;
- license and rights posture;
- capability discovered;
- canonical LiOS owner;
- reuse method/disposition;
- material modifications;
- dependencies;
- security/privacy implications;
- packaging/provisioning implications;
- validation evidence;
- SI workstream contribution;
- Shipping Point contribution.

New donors outside the original 92 baseline must be accounted for separately unless the canonical registry is explicitly expanded. Do not silently rewrite historical baseline counts.

# 6. Donor operating tiers

These tiers describe maintenance posture. They do **not** restrict reuse.

## Tier A — Strategic / controlled mirror

Frequently used or strategically important donor. Usually forked and actively inspected or maintained.

## Tier B — Approved / ready donor

Known useful donor that may be used, forked or promoted immediately whenever relevant.

## Tier C — Specialist / triggered donor

Capability-specific donor. Activate when the relevant requirement or benchmark appears.

## Tier D — Reference validator / challenger

Useful for algorithms, architecture patterns, tests, benchmarks, UX mechanisms, conformance or challenger outputs. May later be promoted to direct implementation.

## Tier E — Restricted / rejected with evidence

Direct reuse is currently blocked by a concrete reason such as incompatible rights, unacceptable security posture, impossible packaging constraint or irreconcilable duplicate authority.

Tier E is not permanent merely because an older review placed it there. Reconsider when facts change, except where legal/rights restrictions remain decisive.

# 7. Donor reuse depth

A donor may contribute at one or more depths:

1. **Idea / pattern** — interaction, scheduling, recovery, state or architecture mechanism.
2. **Algorithm** — adapt behavior with LiOS tests/contracts.
3. **Library** — consume pinned dependency directly.
4. **Component** — import/adapt bounded subsystem.
5. **Runtime** — reuse substantial runtime capability behind stable LiOS contracts.
6. **Challenger / validator** — compare donor behavior/output against LiOS for validation, regression or reconciliation.

Different subsystems from the same donor may use different depths.

# 8. Mandatory donor search before greenfield work

Before substantial new implementation, agents must use this decision order:

> **INSPECT CURRENT LIOS → SEARCH CONTROLLED MIRRORS → SEARCH THE 92-DONOR BASELINE → SEARCH ADDITIONAL EXTERNAL DONORS → ANALYZE → DECOMPOSE → DIRECT REUSE → IMPORT → ADAPT → MODIFY → REPURPOSE → COMBINE → GENERALIZE → INNOVATE → WRAP → BUILD NEW LAST**

A major capability should be built substantially from scratch only when donor leverage cannot produce an equally good or better LiOS implementation without unacceptable legal, architectural, security, maintenance or performance cost.

`REJECT_WITH_EVIDENCE` remains the last option.

# 9. Cross-donor engineering is encouraged

There is no one-donor-per-capability rule.

Agents should combine complementary mechanisms when that produces a stronger LiOS capability.

Example research/agent composition:

> OpenClaw runtime + browser-use browser mechanics + CUA computer-use/isolation patterns + GraphRAG graph research mechanisms + LangAlpha workflow continuity + LiOS P4/P5/P7 authorities = one governed LiOS intelligence capability.

Example Finance composition:

> Qlib quantitative research + FinRobot finance orchestration + TradingAgents adversarial analyst workflows + FinGPT specialist financial NLP + LangAlpha Living Thesis mechanisms + LiOS deterministic P11 engines = LiOS Financial Super Intelligence.

The final user-visible capability remains LiOS. Donor-specific stores, runtimes or product shells must not leak into the product unless explicitly required for compatibility and still governed by LiOS.

# 10. Non-negotiable donor safeguards

Aggressive donor reuse does not override these requirements.

## Licensing and rights

Forking does not change the donor's original license.

Verify exact path/version/license and separate code rights from data/API/model/asset/trademark rights.

Required notices and provenance must be preserved.

## Canonical authority

No donor may accidentally create a second or competing:

- Gateway;
- runtime;
- router;
- database/persistence authority;
- Project authority;
- Conversation authority;
- Working Context authority;
- durable memory authority;
- Artifact authority;
- entity/instrument authority;
- provider registry;
- deterministic finance engine;
- permission/authentication authority;
- plugin/MCP/skills authority.

When LiOS already owns the concept, donor mechanics integrate **inside, underneath, through or behind** that LiOS authority.

## Security and privacy

Donor code must obey LiOS execution, permission, secret, isolation, network, entitlement, provenance and data-transmission policy.

## Product identity

LiOS remains the shipped product. Donor terminology belongs in provenance, notices and advanced diagnostics unless technically required.

## Validation

Upstream tests are useful evidence, not LiOS acceptance. Imported capability requires LiOS-focused validation and the applicable Shipping Point journey.

# 11. Required donor decision record

Every substantial issue/PR must record the donor-first decision at a level proportionate to the change.

Record:

- SI phase/workstream;
- target Shipping Point or direct-enabler rationale;
- canonical LiOS owner;
- controlled mirrors searched;
- relevant 92-baseline donors searched;
- additional donors searched/discovered where useful;
- selected donor(s)/subsystems/mechanisms;
- exact source/pin/path/license before import;
- reuse depth and disposition;
- modifications;
- overlapping alternatives and why they were not selected;
- notices/SBOM/provenance implications;
- packaging/provisioning implications;
- upstream tests reused/ported where useful;
- LiOS validation evidence;
- truth state after merge.

The goal is traceability, not bureaucracy. Small changes may record this compactly; major imports require fuller evidence.

# 14. Scope expansion rule before Foundation Lock

Until SP-01 through SP-04 are accepted, new major capability families should normally enter the active build only when they:

- remove a Foundation Shipping Point blocker;
- prevent material architectural rework;
- are dependency-safe and do not delay the active SP;
- or are already-authorized bounded work that can proceed without shared-core conflict.

This rule does **not** restrict donor discovery, analysis, forking or experimentation.

Agents may continue to discover and evaluate donors at any time.

Large downstream integrations that do not help the current foundation should be recorded in the Post-Foundation Expansion Queue rather than allowed to destabilize convergence.

Examples:

- deeper Qlib/TradingAgents/FinRobot/FinGPT/LangAlpha integration → primarily SI-05;
- deeper CUA/cross-device/autonomy capability → primarily SI-06;
- major new product families → after foundation unless needed to remove a concrete blocker.
