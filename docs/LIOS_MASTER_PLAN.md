## 3. Five product primitives

### 3.1 Projects

A Project is the durable unit of work. A project may contain:

- chats;
- entities and securities;
- files and imported datasets;
- connected-source rules;
- models and assumptions;
- charts, tables and screens;
- reports and notes;
- automations;
- branches/scenarios;
- decisions and saved outputs.

Examples: “NVIDIA Investment Thesis”, “India Macro”, “My Portfolio”, “M&A Target Screen”.

### 3.2 Conversations

Conversation is the primary command surface. Users state intent instead of navigating internal modules.

Examples:

- “Value Reliance using DCF and compare it with peers.”
- “Only use filings and my imported estimates.”
- “Make the downside case harsher.”
- “Why did my valuation change from the previous version?”
- “Run this every earnings season.”

Conversation is executable: it can retrieve data, invoke deterministic engines, mutate explicit project state, create artifacts and schedule monitors.

### 3.3 Artifacts

Important outputs are live typed objects, not text pretending to be analysis.

Core artifact classes include:

- Chart;
- Table;
- Screen;
- Company Workspace;
- DCF / Valuation Model;
- Portfolio / Risk View;
- Scenario;
- Research Note;
- Report / Memo;
- Dashboard;
- Dataset;
- Watchlist;
- Monitor.

Artifacts are reusable, editable, branchable, exportable and addressable from chat.

### 3.4 Connectors

LiOS does not need to own all financial data. It must know how to work reliably with the world’s data.

Connectors cover:

- user files;
- databases;
- cloud storage;
- public data;
- exchange/regulatory sources;
- keyed/premium APIs;
- custom REST/JSON sources;
- analytical sidecars;
- AI providers;
- future MCP/tool providers.

### 3.5 Automations

Any successful workflow may become persistent:

- update after earnings;
- monitor a thesis;
- rerun a screen;
- alert on valuation/risk conditions;
- refresh a report;
- track portfolio events;
- detect data/provider failures.

## 3.6 Quick Chats and temporary/private chats

Not every question needs a Project.

**Quick Chats** sit outside Projects for exploratory work. They may later be moved into a Project with an explicit scope preview showing which files, memories, objects and permissions will change.

**Temporary/private chats** are intentionally non-durable. They do not automatically enter Project memory or long-lived analytical context. They still obey authorization, retention and local-storage policy.

Moving or promoting context between scopes must always be explicit.

## 3.7 Project Home and Project Context

A Project is not just a folder of chats. It has a **rich adaptive Project Home** that can expose the Project's current intelligence state without becoming a manual dashboard-builder.

Depending on the Project and available verified data, Project Home may expose:

- Ask within this Project;
- Project summary;
- pinned priorities/goals;
- What Changed and important Signal/attention items;
- verified key metrics;
- live/recent Artifacts and models;
- recent Chats;
- catalysts/events;
- active Automations/alerts;
- relevant entities/relationships;
- source/data/AI health when useful;
- a compact activity/intelligence timeline.

LiOS may reorder unpinned modules based on materiality/relevance while preserving pinned user items. The dashboard adapts from Project context; users are not forced through a Project-template gate. There is no required permanent Decision widget. Project Home quietly refreshes whenever permitted, but every quantitative state retains source/as-of truth; if current refresh cannot be established, LiOS shows the last verified state/as-of or an explicit unavailable/data-gap state rather than implying freshness.

Detailed complexity remains available on demand through Project settings/context surfaces, Evidence/History, Artifacts, Automations and expanded workspace. Hidden Working Context used by orchestration is not exposed as a normal user-facing inspector.

Project Home must never become a mandatory dashboard-builder.

- scenario values;
- artifact references;
- model versions;

The Ledger is not a transcript dump. It is typed project state.

This enables questions such as:

- “Refresh this with the latest filing but keep my assumptions.”

## 5.1 Five-level context model

LiOS resolves context through five explicit levels:

1. **User context** — locale, timezone, display preferences, default currency/market, accessibility/density preferences and permitted reusable defaults.
2. **Project context** — project instructions, entities, portfolios, files, datasets, models, assumptions, sources, members, data policy and AI policy.
3. **Chat context** — the current thread, references, branch lineage, chat-only attachments and unresolved work.
4. **Workspace context** — active tool/object, period, frequency, currency, scenario, tabs/panes, selections and visible series.
5. **Object context** — the exact model/chart/table/cell/series/range and object version targeted by an action.

Authorization, tenant, entitlement and retention policy form a separate mandatory envelope around every level.

Context precedence is:

> explicit request/reference → explicit UI selection → active workspace object → chat reference → project defaults → user defaults.

Material ambiguous actions must not guess across projects or clients.

Context transitions are typed as:

- `preserve`;
- `extend`;
- `replace`;
- `fork`;
- `clear`;
- `promote`;
- `link`.

This context system is what makes follow-ups such as “make that quarterly”, “only cloud”, “use the same peer set”, or “export this” safe and precise.

## 5.2 Project isolation and AI/data policy

Project storage and mutation authority remain scoped. Relevant retrieval may span all permitted connected sources under the owner-approved 2026-10-02 policy.

- Project A may retrieve relevant Project B evidence only within the user's approved scope and applicable tenant/client/source restrictions, with attribution and exclusions. Existing narrower settings are preserved on migration.
- Global connections do not imply universal project access.
- Each project may restrict which providers, files, databases and AI providers/models may be used.
- Cloud AI may be disabled for private project material.
- Local-only/no-external-AI mode must remain possible.
- Sharing one chat/artifact does not implicitly share an entire project.
- Provider entitlements and licensing remain enforced on shared/forked objects.
- Switching AI providers does not change ownership of Project state.

Prescriptive outputs should remain evidence- and engine-backed, expose assumptions and trade-offs, and make it easy to open the relevant model/source/scene rather than hiding reasoning in prose.

### DecisionArtifact

DecisionArtifact/Decision Object is a first-class structured output with:

- objective;
- constraints;
- alternatives;
- assumptions;
- expected outcomes;
- risks;
- trade-offs;
- selected option where the user chooses one;
- implementation steps;
- monitoring/trigger conditions.

This supports portfolio rebalance, hedging, capital allocation, capital structure, valuation decisions, personal-finance decisions and future domains.

### Voice and multimodal

Voice is an input/output modality over the same Conversation Runtime, not a second product.

Optional local speech runtime may be packaged separately. whisper.cpp is an approved candidate for the optional Voice Runtime Pack. Voice commands must resolve to the same typed intents, permissions, tools and artifacts as text.

### Workspace action permissions

Agent-requested actions are governed by explicit permission classes such as:

- SAFE_AUTO;
- USER_CONFIRM;
- ADMIN_CONFIRM where enterprise policy requires it;
- DENIED.

Read-only navigation and opening local views may often be safe. Material model changes, external writes, trade/order actions or other high-impact effects require the applicable confirmation/policy. Initial autonomous finance workflows remain research/analysis oriented unless a later controlled execution capability is explicitly approved.

### Continuous intelligence

Successful analytical workflows should be savable as repeatable workflows with manual, scheduled or event-triggered execution.

Examples:

- refresh thesis after earnings;
- rerun a valuation after a filing;
- monitor portfolio risk or intrinsic-value thresholds;
- refresh a report;
- run a recurring screen;
- detect provider/data-health failures.

### Personal Finance & Wealth expansion

The Personal Finance & Wealth family may cover, when the user supplies the required data and permissions:

- account/transaction imports;
- cash-flow and net-worth views;
- investments and asset allocation;
- debt/loan planning;
- goals;
- retirement/long-horizon scenarios;
- tax-aware analysis where rules/data are valid;
- insurance/estate-document context where appropriate;
- household scenarios;
- portfolio monitoring.

The emphasis is context + workflow + understandable decision support, not a generic portfolio dashboard.

### Plugin and SDK model

LiOS should become extensible without arbitrary renderer code.

Future SDK boundaries may include:

- Connector SDK;
- Tool SDK;
- Artifact SDK;
- Agent SDK.

Plugin manifests declare permissions, runtime needs, tools/connectors/artifacts, version and dependencies. Marketplace-style distribution is deferred until signing, trust and permission mechanisms are mature.

### MCP strategy

MCP is first-class interoperability.

LiOS should:

- consume approved MCP resources/tools as an MCP client;
- later expose selected governed LiOS tools/data as an MCP server where permissions, Project scope and data rights allow it.

MCP never bypasses Project/tenant/permission/secret boundaries.

### Browser/web intelligence

Playwright or equivalent browser automation belongs in an isolated, permissioned connector/runtime, not the renderer. Require explicit domain and capability policy, bounded resources, timeouts and controlled file/download access.

### Shareable local Project/Session package

LiOS should support a portable Project/Session package (for example a LiOS-specific package or ZIP) containing only permitted state/artifacts/models/data snapshots and excluding credentials/secrets. Imported packages must re-evaluate data entitlements and permissions on the destination machine.

### Runtime Packs and P11 Hidden Engine Fabric

The desktop distribution remains **Core-first, local-first and on-demand**.

P10 establishes preliminary Runtime Packs. **P11 turns that foundation into the full Hidden Engine Pack / OSS Engine Fabric.** The product must be able to assimilate tens or hundreds of permissively licensed engines without exposing donor brands or coupling Project/Conversation/Artifact state to those repositories.

P11 internal pack families are:

- Core Finance;
- Portfolio;
- Pricing & Risk;
- Quant & Forecast;
- Strategy & Backtest;
- Research & Documents;
- Data Lab;
- Market Data;
- Broker & Execution;
- Reporting & Modeling;
- Local AI.

Voice remains a separate modality/runtime concern in P12 and may still use an optional local Voice pack, but it is not the definition of P11.

P11 rules:

- users request **LiOS capabilities**, never upstream library names;
- every candidate is classified immediately as LIBRARY / VENDOR / SIDECAR / CONNECTOR / REFERENCE / REJECT;
- no implementation task remains in a vague "adapt later" state;
- capability routing uses LiOS-owned primary/validator/fallback roles;
- Python packs use isolated locked environments rather than one giant interpreter environment;
- C++/Java/.NET/heavy runtimes execute as supervised local sidecars when that is the stronger integration boundary;
- control messages use the LiOS Engine Protocol; large datasets use Arrow/Parquet/local analytical handles rather than giant JSON;
- packs are signed, hashed, versioned, health-checked, updateable and rollback-safe;
- packs carry SBOM/notices and exact upstream governance;
- optional packs must never make the base app unusable when absent;
- packs never own canonical Project data, credentials, security identity or Artifacts.

The implementation specification is `docs/technical/P11_ENGINE_FABRIC_SPEC.md`; the concrete OSS decision inventory is `docs/technical/P11_OSS_CANDIDATE_MATRIX.md`; the branch-only machine-readable proposal inventory is `third_party/p11-candidates.json`.

### CLI / HQTUI role

HQTUI remains suitable for an optional real-terminal experience such as:

- lios status;
- lios doctor;
- lios connectors;
- lios runtime;
- lios logs;
- lios agents;
- lios data.

It is not the React desktop renderer.

### Final product principle

**Conversation is the interface. Projects are the memory. Data Fabric is the reach. Finance engines are the authority. Agents are the workforce. Artifacts are the work product. Automation is the continuity.**

The implementation must keep the surface simple while allowing professional depth underneath.
